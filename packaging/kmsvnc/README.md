# kmsvnc для dno-tool

Полные исходники с доработками находятся в отдельном форке
[xp9k/kmsvnc](https://github.com/xp9k/kmsvnc).
Сборка закреплена на commit `d766c49283759b4060303f80bbddf49afacbebc8`;
SHA-256 архива проверяется перед распаковкой. Лицензия GPLv3 сохранена.

При наличии локального клона `src/` сборка использует его файлы, исключая `.git`.
Этот каталог не входит в репозиторий dno-tool. Чтобы работать с исходниками:

```bash
git clone https://github.com/xp9k/kmsvnc.git packaging/kmsvnc/src
git -C packaging/kmsvnc/src checkout d766c49283759b4060303f80bbddf49afacbebc8
```

Основа: [isjerryxiao/kmsvnc](https://github.com/isjerryxiao/kmsvnc),
commit `190db24b727e556e234497c1ce38b88cd6668544` от 25.06.2024.
SHA-256 исходного upstream-архива:
`c1bed53c23daecb8cf0d37519180dbbb745d9ef32ef01955a28da9c7723356e3`.

Доработки dno-tool:

- ABGR/XBGR для VAAPI, включая 10-битные буферы Intel/KWin.
- NVIDIA, Intel, AMD: EGL/GBM импорт DMA-BUF с модификатором (и несколькими
  плоскостями, Intel CCS), чтение RGBA через GLES. На каждом кадре читается
  текущий буфер каждого монитора: Xorg и композиторы переключают буферы
  (page flip, вход пользователя, DPMS). Для Intel и AMD GBM открывается на
  render node с правом записи; если EGL не запускается (причина в журнале),
  остаётся VAAPI, который пересоздаёт поверхность при смене буфера.
  Выходы объединяются в один рабочий стол по реальной геометрии KWin,
  сервер передаёт стандартную схему ExtendedDesktopSize и имена разъёмов.
- Абсолютная мышь без конфликтующих REL_X/REL_Y; пробуждение экрана (`-w`)
  нажатием Shift, без перемещения курсора в горячий угол KWin.
- Вертикальное и горизонтальное колесо, повторы клавиш, Shift для символов.
- Поиск символов по всем настроенным раскладкам и соответствие Unicode keysym.
- Учёт клавиш и кнопок отдельно для каждого клиента, отпускание при отключении.
- Миниатюры dno-tool (`thumbnail.c`): клиент объявляет псевдокодировку 0x444E4F54,
  после подтверждения сервера присылает желаемый размер (сообщение 0xC4), и
  сервер отдаёт этому клиенту кадр, уменьшенный в целое число раз средствами
  libvncserver. Остальные клиенты получают полный кадр. Если подключены только
  клиенты миниатюр, экран снимается по их запросам (иначе 30 кадров/с, почти
  ядро процессора), сразу после подключения клиента и смены размера: с версии
  расширения 2 клиент ставит флаг снимка в сообщении размера перед каждым
  запросом кадра, сервер удерживает ответ (`onHold`) до готового снимка.
  Клиенту без флага (dno-tool до 0.15.12) экран снимается раз в секунду.
  С версии 3 (0.0.6-14) есть вторая псевдокодировка 0x444E4F4C — «живой»
  клиент (окно VNC dno-tool на экране 4K): то же подтверждение и сообщение
  размера, уменьшенный кадр, но съёмка как у полного клиента, без удержания.
  Прежний kmsvnc эту псевдокодировку не знает, и окно получает полный кадр.
- Захват (0.0.6-14): экран снимается, только пока клиент полного кадра ждёт
  обновления (открыт запрос), и сразу по его запросу или вводу, не чаще
  `--fps`; после секунды без изменений и ввода — раз в 100 мс. Изменения
  отмечаются плитками 64×64 и копируются только изменённые плитки. Один
  монитор читается сразу в буфер сервера. `--debug` раз в 10 с пишет время
  захвата и сравнения.

## libvncserver

libvncserver 0.9.15 встроена в программу статически: архив закреплён в
`build.sh` (`LVS_SHA256`), версия — `%global lvs_version` в `kmsvnc.spec`.
Системная библиотека не подходит: в МОС 12 это 0.9.13, в МОС 13 — 0.9.15 под
тем же soname `libvncserver.so.1`, но с другой раскладкой `rfbClientRec`
(`UPDATE_BUF_SIZE` 30000 → 32768 сдвигает `sendMutex`, `extensions` и
следующие поля). Кроме того, 0.9.13 держит буферы Zlib/Tight в TLS потока
отправки и теряет их при каждом отключении клиента. Собирается только серверная
часть без TLS, SASL и websockets; zlib, libjpeg и libpng остаются системными.
Пакет больше не зависит от `lib64vncserver1`.

Патч `libvncserver-detach-client-thread.patch` (в spec — `Source2`, применяется
к каталогу libvncserver, а не к kmsvnc): поток клиента создаётся присоединяемым,
а присоединяет его только `rfbShutdownServer`, поэтому каждое обычное
отключение оставляло стек и TLS потока (около 20 КиБ RSS и 8 МиБ адресов).
Ошибка есть и в 0.9.13. Обновления безопасности libvncserver из репозитория МОС
к kmsvnc не применяются: новая версия — замена `lvs_version` и `LVS_SHA256`,
проверка патча и пересборка.

## Сборка RPM

Из корня репозитория на Windows:

```powershell
.\scripts\build_kmsvnc.ps1
```

На Linux с Podman или Docker:

```bash
bash packaging/kmsvnc/build.sh dist/kmsvnc
```

Скрипт собирает бинарный RPM и SRPM в закреплённом контейнере ROSA 2021.1
с пакетами из репозитория МОС 12. Контейнер и зависимости требуют сети.
В SRPM входят полные исходники из закреплённого архива или локального `src/`.

Для сборки напрямую сначала клонируйте исходники, как показано выше.
Нужны CMake, GCC, make, pkg-config и заголовки
libdrm, LibVNCServer, xkbcommon, libva, libva-drm, EGL, GLESv2, GBM, json-c.
Без `-DKMSVNC_LIBVNCSERVER_PREFIX=<каталог установки статической libvncserver>`
берётся системная библиотека — только для локальных опытов:

```bash
cmake -S packaging/kmsvnc/src -B build/kmsvnc -DCMAKE_BUILD_TYPE=Release
cmake --build build/kmsvnc
```

Пакет содержит программу и лицензию. Службу, пароль и порт создаёт мастер
dno-tool. После обновления RPM нужно обновить имя, версию и SHA-256 в
`src/workers/setup/installers/kmsvnc.py`, затем заменить файл в `assets/remote/`.

## Особенности

Ввод идёт через `/dev/uinput`, захват — через DRM. Служба запускается от root.
Для русской клавиатуры используется `XKB_DEFAULT_LAYOUT=us,ru`; активную
раскладку выбирает удалённый графический сеанс. NVIDIA/Wayland автоматически
передаёт полный рабочий стол, Intel и AMD — тоже при захвате через EGL.
Геометрию KWin получает модуль C `screen_layout.c` через штатные утилиты
системы. Для остальных видеодрайверов сохраняется прежний путь захвата. Параметры `--source-plane/--source-crtc`
позволяют явно ограничить захват одним выходом. Для такого режима
`--input-width`, `--input-height`, `--input-offx`, `--input-offy` задают
соответствие выбранного изображения всему рабочему столу.

Обмена буфером через графический сеанс upstream не реализует. Изменение
разрешения захватываемого экрана требует перезапуска сервера. При DPMS
сохраняется последний кадр, захват возобновляется после пробуждения.

## Проверки сборки 0.0.6-4

На МОС 12 / X11 в VM проверены перемещения и три кнопки мыши, оба направления
прокрутки, латиница и кириллица, Shift/Ctrl/Alt, повторы и отпускание клавиш
при отключении клиента с другим подключённым просмотрщиком.

На МОС 13 / KDE Wayland, GeForce GTX 1060 3GB, драйвер NVIDIA 580.178.04
проверен захват AB30 с модификатором `0x03000000004fe014` через EGL.
Основная служба на порту 5900 передаёт обновляющиеся кадры 2560×1440,
libinput принимает абсолютную мышь, кнопки, клавиатуру и оба направления
колеса. Проверены DPMS и перезапуск с повторным подключением. В конфигурации
с двумя мониторами 2560×1440 выбран первый монитор, а область ввода настроена
на весь рабочий стол 5120×1440 через параметры `--input-width/height`.

## Проверки сборки 0.0.6-5

На том же NVIDIA/Wayland-хосте основной сервер передаёт полный кадр
5120×1440: `HDMI-A-1` слева и `DP-1` справа, каждый 2560×1440.
Проверены содержимое обеих областей, ExtendedDesktopSize с двумя мониторами
и координаты абсолютного ввода по всему рабочему столу. Ручная настройка
ширины ввода больше не требуется. Фронтенд, Veyon, KRFB и x11vnc не менялись.

## Проверки сборки 0.0.6-6

Определение схемы мониторов выполняет модуль C, внешний скрипт не устанавливается.
Проверены сборка RPM, отсутствие скриптов и зависимости от интерпретатора,
разбор повреждённых данных и отрицательных координат, захват двух мониторов
5120×1440 на NVIDIA/Wayland.

## Проверки сборки 0.0.6-7

Расширение миниатюр проверено проверочным сервером в контейнере МОС 12
(libvncserver 0.9.13, синтетический экран 1920×1080, тот же `thumbnail.c`)
и клиентом dno-tool: запрос 320×240 даёт кадр 320×180 без обрезки правого края,
параллельный обычный клиент получает 1920×1080. Проверены рост (500×300 → 640×360),
тот же делитель без пересылки кадра, возврат к полному размеру (0×0) и
делитель 30 (64×36). Сборка RPM без предупреждений компилятора в новом модуле.

## Проверки сборки 0.0.6-9

Проверочный сервер в контейнере МОС 12 со встроенной libvncserver 0.9.15
(собрана как в spec, с патчем) и `thumbnail.c`, под valgrind: функциональная
проверка миниатюр, частота съёмки, 100 циклов подключения миниатюр и полных
клиентов с обрывами — `definitely lost` 0 байт (с системной 0.9.13 было 1,4 ГБ
буферов Zlib). RSS процесса на 150 подключениях полных клиентов и миниатюр со
сменой размера не растёт (без патча — около 20 КиБ на подключение).

На 192.168.1.224 (МОС 12, VM) и 172.16.137.39 (МОС 13, NVIDIA, 5120×1440):
только клиент миниатюр — 2–5 % CPU (было 67 и 77 %), с полным клиентом —
прежние 30 кадров/с. Первый кадр миниатюры 64×36 — около 1–4 КБ вместо 342 КБ и
4,5 МБ. Зависимости пакета без libvncserver. RSS kmsvnc после разового выделения
буферов размеров миниатюр не растёт: 10 полных клиентов и 100 подключений
миниатюр — 0 КиБ (с 0.0.6-7 было около 0,16 МиБ на полного клиента и 20 КиБ
на миниатюру).

## Проверки сборки 0.0.6-10

На 172.19.73.207 (МОС 12, Intel, X11, KWin, модификатор X_TILED) с 0.0.6-9
кадр отставал от экрана на минуты: VAAPI читал буфер, выбранный при запуске
(fb 280), а Xorg выводил другие (277, 278, 282). Окно VNC получало один кадр
при подключении, ввод доходил, но изменений экрана не было. С 0.0.6-10 захват
идёт через EGL (`EGL DMA-BUF capture: Mesa Project`), кадр совпадает со снимком
`import -window root`, часы в кадре сменяются вместе с экраном, CPU с полным
клиентом и миниатюрой — около 18 % (VAAPI — 23–25 %). Первые сборки падали в
iris (`intel_aux_map_init`) на fd карты только для чтения и не находили
конфигурацию pbuffer у Mesa GBM — исправлено до выпуска.
